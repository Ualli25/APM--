# Отчёт по мобильному этапу: лабораторные работы №9–11

**Тема:** мобильный клиент системы «АРМ секретаря Учёного совета»  
**Основа:** проект лабораторной работы №8 (FastAPI, SQLModel, SQLite, REST API).  
**Результат:** адаптивное PWA-приложение, раздаваемое FastAPI по адресу `/mobile/`.

## Лабораторная работа №9. Проектирование

### Цель и пользователи

Цель — дать секретарю совета быстрый доступ к сведениям о составе советов, соискателях, диссертационных делах и заседаниях с телефона. В проекте нет аутентификации, поэтому клиент рассчитан на локальную учебную демонстрацию.

### Экраны и переходы

1. **Обзор** — количество советов, соискателей, дел и ближайшие заседания; быстрые переходы.
2. **Советы** — переключение между советами и их составом.
3. **Соискатели** — список, поиск по имени, создание, изменение и удаление карточек.
4. **Диссертационные дела** — список и форма регистрации дела.
5. **Заседания** — список заседаний, отметка явки и результат проверки кворума.

Навигация вынесена в нижнюю панель и доступна на всех разделах. Схемы: [`mobile_architecture.mmd`](mobile_architecture.mmd), [`mobile_user_flow.mmd`](mobile_user_flow.mmd).

### Архитектура и данные

Клиент на HTML/CSS/JavaScript обращается к REST API FastAPI. API валидирует входные схемы, SQLModel выполняет операции с SQLite. PWA манифест описывает установку на главный экран; Service Worker кэширует только статическую оболочку и не кэширует ответы API с данными. Записи хранятся на стороне сервера в `database.db`, браузер не является источником постоянного хранения.

## Лабораторная работа №10. Реализация

Реализованы пять разделов, переходы между ними, загрузка и обновление данных из API, состояния загрузки и ошибок соединения. В карточках соискателей есть CRUD и поиск; в делах — добавление записи; в заседаниях — сохранение списка присутствующих и отображение результата кворума.

Основные проверки формы: ФИО обязательно (3–200 символов), тема диссертации обязательна (8–500 символов), совет/соискатель/специальность должны быть выбраны. Сервер повторно валидирует схему и существование связанных записей. Ошибки отображаются рядом с формой или как уведомление. Удаление соискателя, связанного с делом, отклоняется сервером с HTTP 409.

### Почему PWA

На доступной машине не установлен Flutter SDK, а его архив занимает около 1,9 ГБ. Чтобы выполнить мобильный этап без длительной установки и не менять основу лабораторной №8, создан адаптивный PWA-клиент. Он работает в мобильном браузере и может быть добавлен на главный экран, но не является нативным Flutter-приложением и не собирается в APK. Если преподаватель требует именно Flutter, этот клиент нужно перенести на Flutter как отдельный следующий шаг.

## Лабораторная работа №11. Проверка и интеграция

### Тест-сценарии

| № | Сценарий | Ожидаемый результат |
|---:|---|---|
| 1 | Открыть `/mobile/` | HTTP 200, загружается оболочка приложения |
| 2 | Открыть обзор при работающем API | Показаны данные системы |
| 3 | Перейти по всем пяти пунктам навигации | Каждый раздел отображается |
| 4 | Найти соискателя по части ФИО | Список фильтруется без перезагрузки страницы |
| 5 | Создать корректную карточку соискателя | API возвращает 201, запись появляется в списке |
| 6 | Изменить карточку соискателя | Новые данные сохраняются через PUT |
| 7 | Удалить соискателя без связанных дел | API возвращает 204, карточка исчезает |
| 8 | Создать диссертационное дело | API возвращает 201, запись видна в списке дел |
| 9 | Сохранить явку членов заседания | API возвращает явку и вычисленный признак кворума |
| 10 | Проверить кворум заседания | Отображаются присутствующие, требуемое количество и профильные доктора |

### Негативные сценарии

1. ФИО короче трёх символов — клиентская проверка формы и/или HTTP 422 API.
2. Пустая тема или тема короче восьми символов — форма не отправляется; API возвращает 422.
3. Несуществующая специальность при создании соискателя — API возвращает 404, запись не создаётся.
4. Удаление соискателя, связанного с диссертацией — API возвращает 409 и сохраняет связанную запись.
5. Передача в явке ID члена, который не относится к совету — API возвращает 422.
6. Потеря связи с сервером — клиент показывает уведомление об ошибке и предлагает повторить загрузку.

### Выполненные автоматические проверки

`tests/test_api.py` проверяет списки и поиск членов, создание/изменение/удаление, валидацию, отсутствующие записи и справочники, CRUD соискателя, конфликт удаления связанной записи, раздачу PWA, ограничения внешних ключей, явку, кворум, протокол и отсутствие хеша пароля в ответах API. На момент подготовки отчёта: **16 тестов прошли** командой `.venv\Scripts\python.exe -m pytest -q`.

## Запуск и демонстрация

1. В корне проекта создать/активировать `.venv`, установить `requirements.txt` (если ещё не установлены зависимости).
2. Запустить `python -m uvicorn app.main:app --reload`.
3. Открыть `http://127.0.0.1:8000/mobile/` на компьютере или в мобильном браузере.
4. Для показа с телефона в той же Wi-Fi сети запустить Uvicorn с `--host 0.0.0.0`, узнать локальный IP компьютера и открыть `http://<IP>:8000/mobile/`.
5. Показать обзор, поиск соискателя, создание/редактирование карточки, регистрацию дела и проверку кворума.

Данные для обзора создаются приложением при первом старте, если база пуста. Не оставляйте порт доступным в публичной сети: в проекте учебного прототипа нет входа и управления доступом.

## Итог

Подготовлен мобильный интерфейс из пяти экранов, взаимодействующий с серверной базой и API проекта лабораторной №8. Реализованы CRUD одного основного типа записей, поиск, формы с проверкой, фиксация явки и проверка кворума. Серверные и интеграционные проверки защищают связанные записи от некорректного удаления и отклоняют неверные данные. Отличие реализации от нативного задания — использование устанавливаемого PWA вместо Flutter APK; причина и путь переноса описаны выше.
